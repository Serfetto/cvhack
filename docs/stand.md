# Проверка стенда LinQ — 24.10.2026, 10:55 МСК

## Подтверждено

- VPN подключён: маршрут к `10.0.114.0/24` идёт через туннель `utun7`.
- `hackathon.lin-q.ru` через DNS-запрос разрешается в `10.0.114.30`. Safari не смог разрешить имя, но JupyterHub доступен по `http://10.0.114.30/`; вход под учётной записью команды выполнен.
- В JupyterLab доступны терминал и Python Console. Ядро Console: Python 3.11.6, `/opt/conda/bin/python`.
- В контейнере Jupyter нет `/dev/tpu*`, а `import pytpu` завершается `ModuleNotFoundError`. Поэтому `pytpu.Device.list_devices()` здесь не является способом проверки ускорителя.
- В `examples/` есть `example.ipynb`, тестовый JPEG и программа `torch_resnet50_b1_o5_h1m.tpu`. В `packages/` есть `tpu_pycloud_format-0.0.1-py3-none-any.whl`; `pika` и `tpu_pycloud_format` уже доступны в ядре.
- Эталонный пример отправляет тензор через RabbitMQ (`10.0.114.30:5672`, exchange `tpu.direct`), указывая путь к `.tpu` в персональном `/auto/cache/<логин>/`. TCP-порт `5672` доступен и с локального Mac через VPN. Аутентификация в брокере с Mac пока не проверена.
- Программа ResNet50 скопирована в персональный cache стенда. Три запроса вернули `status_code=0` и ожидаемый класс `257` (Newfoundland dog). Время **от отправки задачи до ответа**: первый запрос 8,14 с, следующие 0,40 и 0,22 с. Это не чистая задержка TPU и не бенчмарк FPS.

## Вывод для интеграции

Доступный команде Jupyter — клиент облачного сервиса инференса LinQ, а не хост с прямым `/dev/tpu*`. Описанный в `ARCHITECTURE.md` вариант `pytpu` внутри Jupyter для этой учётной записи не подтверждён. Ближайший рабочий путь: компилировать модель в `.tpu`, загружать её в персональный cache и отправлять задачи по протоколу примера (`pika` + `tpu_pycloud_format`). Нужно согласовать этот контракт с бэкендером до реализации `inference-service`.

## Ответы техподдержки от команды

- Свои очереди RabbitMQ разрешены, заявленный предел сообщения около 16 МБ; допустимы квантованные данные и raw-режим. Для обмена с нашим сервером можно пересылать JPEG, оставляя пре- и постобработку в Jupyter.
- Облачный сервер постобработки существует, но команде предоставлен только доступ к брокеру.
- Очередь `input` общая для команд, её обслуживают 16 TPU. Задачи можно отправлять без ожидания ответа и использовать batch; `?raw=True` поддерживается.
- Jupyter не выключается при простое, фоновый процесс допустим; `~/work` и персональный `/auto/cache/` сохраняются до конца хакатона.
- На Jupyter выделены 1,5 CPU и 4 ГБ RAM; своё Python-окружение разрешено.
- Программы SDK `2026.9.45` совместимы с облачным рантаймом. Отдельного канала для баг-репортов нет.

Эти сведения получены из ответа поддержки; ограничения по размеру сообщения были указаны ориентировочно («16 МБ кажется»), поэтому перед передачей больших тензоров нужен практический тест.

## Осталось проверить

1. Получить SDK компиляции, собрать и запустить собственную YOLO-программу `.tpu`; зафиксировать имена и формы входов/выходов.
2. Проверить аутентификацию и отправку AMQP-задачи непосредственно с хоста бэкенда через VPN.
3. Измерить задержку и FPS на серии кадров с разделением подготовки кадра, очереди, инференса и обработки выхода; отдельно проверить поведение при параллельных потоках.
4. Реализовать воркер в Jupyter, принимающий JPEG из своей очереди и отправляющий задачи TPU через общую `input`; прямой `pytpu` в текущем окружении не требуется.
